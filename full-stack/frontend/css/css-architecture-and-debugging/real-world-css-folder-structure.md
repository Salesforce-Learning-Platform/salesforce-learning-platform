# 📁 A Real-World CSS Folder Structure

## A Structure That Mirrors This Module's Own Concepts

```
styles/
├── main.scss                 ← the single entry point, per partials-and-imports.md
├── base/
│   ├── _reset.scss           ← browser default resets
│   ├── _typography.scss      ← global heading/body text rules
│   └── _variables.scss       ← Sass variables and CSS custom properties
├── layout/
│   ├── _header.scss          ← page-level structural regions
│   ├── _footer.scss
│   └── _grid.scss
├── components/
│   ├── _product-card.scss    ← one file per component, per component-based-css.md
│   ├── _button.scss
│   └── _navbar.scss
└── utilities/
    └── _spacing.scss         ← small, single-purpose helper classes
```

This folder structure gives every kind of style a clear, predictable home — directly the physical
expression of
[scalable-backend-structure.md](../../../backend/backend-architecture/scalable-backend-structure.md)'s
"a project's real architecture should be visible from its file tree" idea, applied to CSS instead
of a backend codebase.

## `base/` — Global, Foundational Styles

Resets, base typography, and centralized variables (both
[Sass variables](../working-with-sass/variables.md) and
[CSS custom properties](../css-core-fundamentals/css-variables.md)) belong here — the small set of
genuinely global rules every other file builds on top of.

## `layout/` — Large, Structural Regions

A page's header, footer, and overall grid are structural, not really "components" in the reusable
sense a product card is — they typically exist exactly once per page, so they get their own
category, separate from genuinely reusable components.

## `components/` — One File, One Reusable Component

Directly [component-based-css.md](component-based-css.md)'s "one component, one file" principle —
this folder should be the largest and most frequently touched, since it's where most of a real
UI's actual visual identity lives.

## `utilities/` — Small, Single-Purpose Helpers

Whether hand-written or generated by a framework (per
[CSS Frameworks](../css-frameworks/)), single-purpose helper classes get their own clearly-labeled
category — making it obvious they're intentionally different in kind from a component's own
BEM-named classes, per
[utility-classes-vs-component-classes.md](utility-classes-vs-component-classes.md).

## `main.scss` — Wiring, Not Styling

```scss
// main.scss
@use "base/reset";
@use "base/typography";
@use "base/variables";
@use "layout/header";
@use "layout/footer";
@use "layout/grid";
@use "components/product-card";
@use "components/button";
@use "components/navbar";
@use "utilities/spacing";
```

`main.scss` itself contains no real styles — only `@use` statements loading every partial in a
sensible order (base styles first, so later files can rely on the variables and resets they
establish) — the CSS equivalent of
[backend-architecture's app.js](../../../backend/backend-architecture/scalable-backend-structure.md)
being "wiring, not logic."

## Common Mistakes

- Mixing structural (`layout/`) and reusable (`components/`) styles in the same folder, losing the
  clear signal about which kind of thing a given file actually represents.
- Letting `main.scss` accumulate real style declarations over time instead of staying pure
  `@use` wiring, defeating the whole point of the organized structure underneath it.
- Copying this exact structure onto a tiny project where it adds more organizational overhead than
  it's worth — the right amount of structure scales with a project's actual size, the same
  reasoning [scalable-backend-structure.md](../../../backend/backend-architecture/scalable-backend-structure.md)
  applies on the backend.
