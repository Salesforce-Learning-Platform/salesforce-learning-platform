# ⚙️ JavaScript Engines and JIT Compilation

## Who Actually Runs Your Code?

JavaScript is a language specification; something has to execute it. That something is a
**JavaScript engine**: V8 in Chrome, Edge, and Node.js; SpiderMonkey in Firefox; JavaScriptCore in
Safari (and in the Bun runtime, as Bun's own site states). An engine takes source text and turns it into
running machine code, and the way it does that explains many performance rules of thumb you may have
heard — "keep your object shapes consistent," "don't change types in hot code" — and, just as
importantly, why most micro-optimization advice is a waste of time.

This file uses **V8** as the worked example, and verifies each claim by asking V8 itself (Node.js 24 uses
V8, so its diagnostic flags work on any script). Those flags are for *learning and debugging*; never rely
on them in production code.

## 🧬 The Pipeline: Interpret First, Optimize What Is Hot

An engine does not compile everything perfectly up front. That would make every page load slow, and most
code runs only once. Instead it starts quickly and spends optimization effort only where the program
spends its time. V8's engineering blog describes the tiers:

| Tier | What it is | Role |
|------|-----------|------|
| **Parser** | Reads source into an abstract syntax tree | Turns text into structure |
| **Ignition** | The interpreter | Compiles to compact **bytecode** and runs it; fast startup, low memory |
| **Sparkplug** | A non-optimizing baseline compiler | Compiles bytecode straight to machine code in one pass (released in V8 v9.1) |
| **Maglev** | A mid-tier optimizing compiler | Fills the gap between Sparkplug and TurboFan; per V8's post it compiles roughly 10× faster than TurboFan (introduced in Chrome M117) |
| **TurboFan** | The top-tier optimizing compiler | Produces highly optimized machine code for the hottest functions |

This approach is called **JIT** (just-in-time) compilation: code is compiled while the program runs,
using information gathered from the running program. That information — which types actually flow
through each operation — is the engine's **type feedback**, and it is what makes optimization possible
for a language as dynamic as JavaScript.

## 👀 Seeing Bytecode

Ignition's bytecode is inspectable. For this tiny function:

```js
function add(a, b) {
  return a + b;
}
add(1, 2);
```

`node --print-bytecode --print-bytecode-filter=add file.js` prints (addresses omitted):

```
[generated bytecode for function: add]
Bytecode length: 6
Parameter count 3
   Ldar a1          // load argument b into the accumulator register
   Add a0, [0]      // add argument a to the accumulator; [0] is a slot for type feedback
   Return           // return the accumulator
```

Three instructions, six bytes. (The parameter count is 3 because the receiver, `this`, counts as one.)
Ignition is an *accumulator machine*: most operations read and write one implicit register, which keeps
the bytecode compact. You will never write bytecode, but seeing it makes "the engine compiles your code"
concrete rather than magic.

## 🔥 Watching Code Get Optimized — and Deoptimized

The next script calls `add` many times with numbers, once with strings, then many times with numbers
again:

```js
function add(a, b) {
  return a + b;
}
for (let i = 0; i < 200000; i++) add(i, 1);   // hot, always numbers
add("a", "b");                                 // a different type!
for (let i = 0; i < 200000; i++) add(i, 1);
```

Run with `node --trace-opt --trace-deopt` and filtering for `add`, the log tells the story (trimmed):

```
marking <JSFunction add> for optimization to MAGLEV, reason: hot and stable
completed compiling <JSFunction add> (target MAGLEV)
bailout (kind: deopt-eager, reason: not a Smi): deoptimizing <JSFunction add>, <Code MAGLEV>
marking <JSFunction add> for optimization to MAGLEV, reason: hot and stable
completed compiling <JSFunction add> (target MAGLEV)
marking <JSFunction add> for optimization to TURBOFAN_JS, reason: hot and stable
completed optimizing <JSFunction add> (target TURBOFAN_JS)
```

Reading it:

1. Called repeatedly with numbers, `add` became **hot and stable**, so V8 compiled an optimized version
   specialized for what it had *seen* — small integers. A **Smi** is V8's compact representation of a
   small integer.
2. The call with strings broke that assumption. The optimized code could not handle it, so V8
   **deoptimized** ("bailout … not a Smi"): it discarded the optimized code and fell back to the
   interpreter, which handles any type.
3. Because the function kept running hot, V8 optimized it again, and later promoted it to the top tier.

Optimization is *speculative*: the compiler bets on the types it has observed and guards the bet. A
deoptimization is the guard firing — correct behavior, merely slower for a moment. The practical lesson
is not "never mix types" (it is fine in code that is not hot) but "in the hottest loops, stable types let
the engine do its best work."

## 🧱 Hidden Classes: Why Object Shape Matters

Property access like `point.x` would be slow if the engine had to search a dictionary every time. V8
instead gives objects a hidden **shape** (V8 calls it a *Map*): a description of which properties exist
and where they are stored. Objects with the same shape can share optimized code, because the offset of
`x` is known in advance. The V8 documentation explains that objects created with the same properties in
the same order follow the same chain of shapes.

V8's `%HaveSameMap` (available only with `--allow-natives-syntax`) lets you verify it:

```js
const p1 = { x: 1, y: 2 };
const p2 = { x: 3, y: 4 };
const p3 = { y: 2, x: 1 };       // same properties, different ORDER
const p4 = { x: 1, y: 2 };
p4.z = 3;                        // a property added LATER

console.log(%HaveSameMap(p1, p2));   // true   — same properties, same order
console.log(%HaveSameMap(p1, p3));   // false  — property order matters
console.log(%HaveSameMap(p1, p4));   // false  — adding a property changes the shape

class Point { constructor(x, y) { this.x = x; this.y = y; } }
console.log(%HaveSameMap(new Point(1, 2), new Point(3, 4)));   // true — constructors give consistent shapes
```

Deleting a property can be worse still: after `delete o.x`, the test object reported
`%HasFastProperties(o) === false`, meaning V8 had switched it to slower, dictionary-style storage.

What this means in practice, in order of importance:

- **Initialize every property in the constructor**, in the same order, rather than adding them
  conditionally later.
- **Prefer `obj.prop = undefined` or `null` to `delete obj.prop`** on objects that are used heavily.
- **Don't treat any of this as a rule to apply everywhere.** It matters in hot paths that touch millions
  of objects; elsewhere, clarity wins.

## 🧭 What to Take Away

- Engines are fast because they *adapt* to your program, not because they understand your intent.
- Consistent types and shapes in hot code let the optimizing tiers do their best work.
- Measure with a profiler ([performance-apis.md](../browser-apis-in-depth/performance-apis.md), DevTools,
  Node's `--prof`/`--cpu-prof`) before changing code for performance. The engine's behavior changes
  between versions; an optimization that helps one year may be irrelevant the next.
- Algorithmic improvements (fewer operations, better data structures — see the
  [Data Structures and Algorithms](../../../data-structures-and-algorithms/) section) dwarf engine-level
  tuning almost every time.

## 🎤 Interview Angle

- **"What is a JavaScript engine?"** The program that parses and executes JavaScript — V8, SpiderMonkey,
  JavaScriptCore — typically with an interpreter plus optimizing compilers.
- **"What is JIT compilation?"** Compiling code while the program runs, using runtime type feedback to
  optimize frequently executed ("hot") code.
- **"What is deoptimization?"** Discarding optimized code when its type assumptions turn out to be wrong,
  falling back to slower code that handles every case.
- **"Why do hidden classes matter?"** Objects with identical shape share optimized property access;
  changing property order or adding properties dynamically fragments shapes.
- **"Is JavaScript interpreted or compiled?"** Both: modern engines interpret to bytecode first, then
  compile hot code to machine code.

## Common Mistakes

- **Micro-optimizing without profiling.**
- **Assuming "interpreted language" means slow**, or that optimization is a fixed property of the language.
- **Creating objects with shapes that vary** (conditional properties, differing order) in performance-critical loops.
- **Deleting properties from hot objects.**
- **Relying on engine-specific flags or behavior** in production code.
