# 🔎 How Similarity Search Works Conceptually

## From "Nearby Vectors" to an Actual Search

[what-embeddings-represent-in-vector-space.md](what-embeddings-represent-in-vector-space.md)
established that similar meaning produces nearby vectors. Similarity search is the concrete
mechanism that turns this idea into a working feature: given a query, find the most relevant
document(s) out of a whole collection.

## Cosine Similarity — Measuring "Closeness"

```
Cosine similarity measures the ANGLE between two vectors, not
their raw distance.

Two vectors pointing in nearly the same direction → similarity
close to 1 (very similar meaning)

Two vectors pointing in very different directions → similarity
close to 0 or negative (unrelated or opposite meaning)
```

Cosine similarity is the standard metric for comparing embeddings — it captures *direction*
similarity in the vector space, which corresponds well to semantic similarity, regardless of how
long or short the original text was.

## A Simplification That Matters in Practice

```python
import numpy as np

# Voyage embeddings are normalized to length 1, so dot product
# and cosine similarity give IDENTICAL results — and dot product
# is cheaper to compute.
similarity = np.dot(query_embedding, doc_embedding)
```

Because Voyage's embeddings are already normalized to a consistent length, a plain dot product
produces the exact same ranking as full cosine similarity, at lower computational cost — a detail
worth knowing since it explains why real embedding code often uses a simple dot product rather than
a more elaborate cosine-similarity formula.

## Finding the Best Match Across Many Documents

```python
documents = [
    "The Mediterranean diet emphasizes fish, olive oil, and vegetables.",
    "Photosynthesis in plants converts light energy into glucose.",
    "Apple's Q4 earnings call is scheduled for Thursday at 2pm PT.",
]
doc_embeddings = vo.embed(documents, model="voyage-4", input_type="document").embeddings

query = "When is Apple's conference call scheduled?"
query_embedding = vo.embed([query], model="voyage-4", input_type="query").embeddings[0]

similarities = np.dot(doc_embeddings, query_embedding)
best_match_index = np.argmax(similarities)
print(documents[best_match_index])
# → "Apple's Q4 earnings call is scheduled for Thursday at 2pm PT."
```

This is nearest-neighbor search in its simplest form: embed every document once, embed the query,
compute the similarity between the query and every document, and return whichever document scored
highest. Notice the query and the matched document share almost no exact words — "conference call"
versus "earnings call," "scheduled" appearing in both — yet the embedding correctly identifies them
as semantically related.

## Why This Doesn't Scale as a Brute-Force Loop Forever

```
3 documents        → compare against all 3 → instant
3,000 documents     → compare against all 3,000 → still fast
3,000,000 documents → comparing against EVERY one, every query →
                       genuinely slow at real-world scale
```

Computing a similarity score against every single document works perfectly for a small collection
like the example above, but doesn't scale to millions of documents queried repeatedly — which is
exactly the problem [Integrating Vector Databases](../integrating-vector-databases/), later in this
domain, solves with specialized indexing structures built for fast approximate search at scale.

## Common Mistakes

- Assuming a higher similarity score always means a *correct* answer, rather than merely the most
  semantically related document available — a collection with no genuinely relevant document still
  returns some "best" match.
- Comparing embeddings generated by two different models (or even the same model without a matching
  `input_type`) as though they exist in the same comparable space — they generally don't.
- Reaching for a brute-force loop over millions of documents in production instead of a proper
  vector index once the collection grows past a small scale.
