# 🗄️ File Systems

## 📚 Overview

A program's variables vanish when it ends, but programs also need data that does not: documents, photos, databases, even the program's own code. The **file system** is the part of the operating system that makes such data durable. It turns a device that offers nothing but numbered blocks into named files in directories, decides which blocks hold what, lets many users and programs share the device, protects each file from the wrong hands, and keeps its own structures consistent even when the machine stops in the middle of an update. Many everyday puzzles come back to the ideas in this module: why a file of five bytes occupies a whole block, why deleting a file can free no space, why a program can keep reading a file that no longer has a name, why a crash can leave a half-written file, and why a read-only file can be deleted while a writable file in a read-only folder cannot.

The module starts with what a file system is for: its five jobs, the layers between a program and the disk, what a formatted volume contains, why space is handed out in whole blocks (with a measurement of how much a pile of tiny files wastes), what a sparse file is, and why updates must be done carefully (journaling, redirect-on-write, and the pattern of writing a temporary file and renaming it). It then follows a name to a file: **inodes**, the metadata that `os.stat` reports, **hard links and symbolic links**, what a **file descriptor** really points to, and how a path is resolved, ending with a small working model of a file system that was tested against the real one on tens of thousands of random operations. Next comes **file allocation**: contiguous, linked (as in the FAT), indexed (the Unix inode with direct and indirect pointers), and extent-based allocation, each built as a class on a simulated disk, with the cost of reaching a block, the largest file an inode can describe, and an experiment on a nearly full disk. The last two lessons are about **protection and security**: first the permission bits and the rule that decides every request, the umask, directory permissions, the setuid, setgid, and sticky bits, and access control lists; then the races and path-traversal tricks that get around correct permissions, and integrity checks, disk encryption, and least privilege. Every code example was run on CPython 3.9 on a Mac (macOS, Apple silicon); machine-dependent results are labelled, and the models were checked against the real file system or against independent references on thousands of random inputs.

## 🎯 Learning Objectives

By the end of this module, you will be able to:

- State the jobs of a file system, name the layers between a program and the disk (system calls, logical file system, virtual file system, physical file system, and block layer), and read the block sizes and free space of your own volume.
- Explain why files occupy whole blocks (slack space), what a sparse file is, and why one logical operation can touch several on-disk structures.
- Explain how journaling and redirect-on-write keep a file system consistent after a crash, and use the write-a-temporary-file-then-rename pattern in your own programs.
- Distinguish a file from its name: describe an inode, a directory entry, the link count, hard links versus symbolic links, what `unlink` does, what a file descriptor refers to, and how a path is resolved (including the limit on symbolic links).
- Compare contiguous, linked (FAT), indexed (inode), and extent-based allocation by fragmentation, random access, growth, and bookkeeping, and calculate the number of reads to reach a block and the maximum size of a file.
- Decide from the permission bits whether a request is allowed (the owner, group, and other classes, and the special meaning of the bits on directories), explain the umask, and recognize the roles of setuid, setgid, sticky bits, and access control lists.
- Recognize and prevent check-then-use races and path-traversal attacks, and explain what integrity fingerprints, disk encryption, and least privilege protect and what they do not.

## 🧠 Knowledge Check

<details>
<summary>A file system uses 4 KiB blocks and Unix-style inodes with 12 direct pointers and one single-, one double-, and one triple-indirect pointer; a block number takes 4 bytes. How many pointers fit in an indirect block? How many disk reads does it take to read byte 20,000,000 of a file (counting the index blocks and the data block, not the inode), and what is the largest file the scheme can describe?</summary>

An indirect block holds 4,096 / 4 = 1,024 pointers. Byte 20,000,000 lies in block 20,000,000 ÷ 4,096 = 4,882 (rounded down). Blocks 0 to 11 are reached by the direct pointers, blocks 12 to 1,035 need the single-indirect block (12 + 1,024 = 1,036 blocks so far), and blocks 1,036 to 1,049,611 need the double-indirect block, so block 4,882 takes three reads: the first-level index block, the second-level index block, and the data block. With linked allocation the same position would mean following about 4,882 pointers, one read each unless the table is cached; the table in [file-allocation.md](file-allocation.md) shows 3 reads for indexed and 5,001 for linked at block 5,000. The largest file has 12 + 1,024 + 1,024² + 1,024³ blocks of 4 KiB each, which is about 4 TiB (the same file shows 4.0 TiB for 4 KiB blocks), while the 12 direct pointers alone cover only 48 KiB.

</details>

<details>
<summary>A file has two hard links, <code>a.txt</code> and <code>b.txt</code>, and a program has it open. What happens to the data when you delete <code>a.txt</code>, then <code>b.txt</code>, and then the program closes the file? What would be different if <code>b.txt</code> had been a symbolic link to <code>a.txt</code>?</summary>

Deleting `a.txt` removes one *name*: the link count drops from 2 to 1 and nothing else changes, because the data belongs to the inode, which `b.txt` still names. Deleting `b.txt` removes the last name, so the link count becomes 0, but the program still has the file open, so the inode and its blocks stay in existence and the program can keep reading and writing through its descriptor (the experiment in [files-and-directories.md](files-and-directories.md) showed a link count of 0 and the data still readable). Only when the program closes the file does the file system free the inode and its blocks; the space of a "deleted" file is therefore not released while any process holds it open. If `b.txt` had been a *symbolic link* to `a.txt`, it would hold only a path, not a reference to the inode: deleting `a.txt` would remove the file's only name (and free the file once nobody had it open), and `b.txt` would **dangle**, pointing at a name that no longer exists.

</details>
