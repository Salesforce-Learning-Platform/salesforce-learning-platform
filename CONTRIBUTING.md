# Contributing

Thank you for contributing to the Salesforce Learning Platform.

This project is designed as an open learning resource covering Salesforce development, full-stack engineering, computer science foundations, and enterprise architecture.

## Before You Contribute

Before creating content or making changes:

1. Check existing issues and discussions.
2. Keep content technically accurate and practical.
3. Use official documentation and reliable sources where applicable.
4. Do not copy content from external sources without permission or attribution.
5. Avoid including confidential, proprietary, or client-specific information.

## How the Repository Is Organized

- Learning content is in [`full-stack/`](full-stack/). The [root README](README.md#getting-started) lists the areas in course order.
- Each area has a home page (`README.md`). Most list every module in learning order with what it builds on; the [frontend home page](full-stack/frontend/README.md) lists its domains, and [Computer Science Foundations](full-stack/computer-science-foundations/README.md) links to a page for each of its two sections.
- `salesforce/`, `architecture/`, `projects/`, and `resources/` hold areas that are still being planned.
- [`docs/`](docs/) holds platform documentation, including the [content standards](docs/content/content-standards.md) and [review guidelines](docs/content/content-review-guidelines.md), which apply to all content.

## Module Structure

A module is a folder with a `README.md` and one Markdown file for each lesson. The module's README has these sections, usually in this order:

| Section | What it holds |
|---------|---------------|
| Overview (or Purpose) | What the module covers and why it matters |
| Learning Objectives | What the reader will be able to do afterwards |
| Prerequisites | Links to the earlier modules or lessons it relies on, with a short reason for each; mark optional ones "(optional)" |
| Module contents (or Files in This Module) | A table of the lessons in reading order |
| When to Deep-Dive vs. Skim | Where to spend time, and what an experienced reader can skim |
| Knowledge Check | At least two questions, each with its answer inside a `<details>` block |
| References | Sources the reader can open |
| Continue Your Learning Path | A link to the next module |

Headings vary a little between modules (many newer ones add icons, such as `## 📚 Overview`), so follow the style of the neighboring modules. Each lesson ends by pointing to the next one, and the last lesson usually ends with a module summary.

### Learning Path Rules

- Following each module's "Continue Your Learning Path" section, starting at [How the Internet Works](full-stack/frontend/foundations/how-the-internet-works/README.md), visits every module in course order. It links to the next module, or, where the path moves to another section, to that section's page.
- A module's required prerequisites must come before it on that path.
- When you add or move a module, update the previous module's link, give the module its own link, and add it to its area or section page.

## Writing and Accuracy

Along with the [content standards](docs/content/content-standards.md):

- Write original text. Use sources to check facts, not to copy wording.
- Check technical claims against primary sources, such as specifications and official documentation, and link them. Never guess a URL or a citation, and open every link you add.
- Run every code example. Show output from a real run, and say when results depend on the machine, runtime, or version.
- Keep documented facts apart from your recommendations, and say when an example is made up.
- Write plainly and explain terms when you first use them. Leave out filler such as "genuinely" and "truly".
- Never include an example that crashes the interpreter or the computer, such as a deliberate segmentation fault. Simulate failures safely.
- Do not hide content in HTML comments or invisible characters, and do not add tool or vendor branding or "generated by" notes.

## Code Standards

Code contributions should:

- Be readable and appropriately documented.
- Follow platform and language conventions.
- Avoid unnecessary complexity.
- Include setup or execution instructions when required.
- Not contain secrets, credentials, or environment-specific information.

## Automated Checks

Every pull request, and every push to `main`, runs [`check_content.py`](.github/scripts/check_content.py). It checks:

- relative links, including the exact letter case of file names;
- links to headings (`#anchors`), using the anchors GitHub creates;
- that Python and JSON code blocks parse. Code is never run.

Run it before you push. It needs Python 3.9 or later and Git, with no extra packages:

```bash
python3 .github/scripts/check_content.py
```

Label code blocks so they can be checked: `json` for JSON, `jsonc` for JSON with comments, `jsonl` for one JSON value on each line, and `text` for diagrams and fragments that are not code. If a Python or JSON block is meant not to parse, for example to show a syntax error, add it to [`content-check-exceptions.json`](.github/content-check-exceptions.json) with a reason; the failure message shows the entry to add. The check also fails when an exception is no longer needed.

Links to other websites are checked weekly by the "External links" workflow, which you can also start by hand. You can run the same check locally with `--external`; it takes several minutes. It fails only for dead links (HTTP 404 or 410, or a host name that no longer resolves). The run summary lists links it could not verify, so they can be checked by hand.

## Contribution Process

1. Find or create an issue. Planned work is titled `OPS-NNN: short description`; maintainers assign the numbers, which are sequential and never reused, and add the issue to the project board.
2. Discuss the proposed change when necessary.
3. Create a branch from `main`, such as `feature/OPS-NNN-short-name`. Do not commit directly to `main`.
4. Make your change and run the checks.
5. Review it twice: once for technical accuracy, and once as a learner would read it on GitHub, including links, tables, and code.
6. Commit with a message such as `docs: add a lesson on window functions (OPS-NNN)`.
7. Open a pull request that explains what changed and how you checked it, with `Closes #<issue number>`.
8. Ensure the contribution meets the issue's acceptance criteria, and address review feedback.
9. A maintainer merges it with a merge commit, deletes the branch, and notes the pull request and merge commit on the issue.

## Important

Do not include confidential information from employers, clients, Salesforce organizations, or other private systems.

Examples may be inspired by real-world experience, but proprietary names, data, configurations, architecture, and business logic must not be disclosed.
